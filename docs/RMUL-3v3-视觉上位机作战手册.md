## 0. 先纠正一个认知（这条最重要）

绝大多数新手对"视觉上位机"的想象是：

> 训练一个模型 → 能框出装甲板 → 完事

实际比赛里，**检测只占你工作量的 25%**。真正决定你能不能打到人的是这四件事：

| 决定成败的环节 | 新手以为的重要性 | 实际重要性 | 失败了会怎样 |
|---|---|---|---|
| 装甲板检测（传统视觉/YOLO） | 80% | 20% | 框到了但打不中，观众看不出问题 |
| **相机标定 + 坐标转换 + PnP** | 5% | 25% | 角度系统性偏 3°，永远差半个装甲板 |
| **弹道解算 + 延迟补偿** | 5% | 20% | 近处很准，5 米外全空 |
| **串口通信 + 帧率稳定性** | 5% | 20% | 平时能跑，一上场就抽风/掉线 |
| 反小陀螺 / 目标预测 | 5% | 15% | 打静止靶百发百中，打旋转目标 0 命中 |

**一句话**：自瞄的难点不是"看见"，是"瞄得准、瞄得稳、发得出去"。
把这个认知装上，你的学习顺序才不会跑偏。

## 1. 你负责什么：职责边界

### 1.1 你的交付物（Definition of Done）

一个能在实车上跑起来的**自瞄系统**，具体是：

1. **一个上位机程序**：从相机取图 → 检测装甲板 → 解算目标相对云台的角度 → 通过串口以 100~1000 Hz 把角度发出去
2. **一套标定数据**：相机内参、畸变系数、相机↔云台↔枪口的外参（旋转 + 平移）
3. **一份串口协议**：你写、电控同学签字确认、双方都留档
4. **一个可复现的部署包**：对方队伍发你一台新主机，你 30 分钟内能跑起来
5. **一份测试报告**：静态靶命中率、移动靶命中率、各距离偏差曲线、帧率与延迟实测

### 1.2 你**不**负责（但要会对接）

| 不归你 | 归谁 | 你要提供/索取什么 |
|---|---|---|
| 云台电机 PID、IMU 姿态解算 | 电控 | 你要 IMU 的 yaw/pitch 角度（相机装底盘时必需） |
| 弹丸初速度、摩擦轮转速 | 电控/机械 | **实测弹速**，这是弹道解算的输入 |
| 相机云台机械安装、走线 | 机械 | 你要确认光轴与枪管平行度 < 0.5° |
| 裁判系统串口读数 | 电控 | 血量、比赛阶段（决定你要不要切模式） |
| 图像传输/图传链路 | 电控/硬件 | 图传占带宽会影响你 USB3.0 带宽 |

### 1.3 三种相机安装方案（**先和队里定这个，它决定后面所有代码**）

| 方案 | 相机装哪 | 你要发给电控的量 | 优点 | 缺点 | 推荐度 |
|---|---|---|---|---|---|
| **A. 相机随云台动** | 云台上，与枪管同轴 | 目标相对相机的 `yaw, pitch` | 视野即枪口方向，闭环简单；电控直接跟角度 | 视野受云台限制，看不到侧后方 | ⭐⭐⭐⭐⭐ **首选** |
| B. 相机装底盘固定 | 底盘，视野不受云台限制 | 需要电控回传云台当前 yaw/pitch，你换算成**相对云台**的角度 | 能提前发现目标，适合"先看后转" | 依赖电控回传，链路多一环，延迟叠加 | ⭐⭐⭐ |
| C. 双相机 | 云台 + 底盘各一 | 融合 | 最全面 | 工作量翻倍，3v3 没必要 | ⭐ |

> **给你的建议**：直接选 A。3v3 场地小、交火距离近（多在 3~8 m），全方位搜索的价值远低于"瞄得准"。把省下的时间全砸在标定和延迟上。

## 2. 硬件盘点：你手上这些东西怎么用

你目前的设备清单，我直接给结论：

| 设备 | 用途定位 | 结论 |
|---|---|---|
| **海康工业相机 (USB3.0/GigE)** | **自瞄主相机** | ⭐ **主力**。全局快门 + 可编程曝光/增益 + 稳定时戳，这是自瞄的刚需。注意确认型号是 `-10UC`(USB3) 还是 `-10GM`(GigE)，GigE 需要千兆网口和 POE 供电 |
| **OAK-D (DepthAI)** | 备选/第二路 | 内置 VPU 能跑 YOLO，省主机算力。但 **输出延迟通常比主机跑 TensorRT 高**（图像要过一遍 VPU 再上传）。适合做"低算力平台方案"，不适合追求极致延迟 |
| **Intel RealSense D435i** | 调试/深度 | **卷帘快门**是硬伤，云台一甩就果冻效应 + 运动模糊。深度信息在打静止靶测距时有参考价值，但**不要拿它当自瞄主相机**。适合当"备用眼睛"或做视觉里程计 |
| **普通 USB 摄像头** | 开发调试 | 只用来写代码调算法，永远不上车。卷帘快门 + 自动曝光 = 灾难 |
| **零刻 / GPD (Ryzen 7840U)** | 机载主机 | 8 核 16 线程 Zen4 + Radeon 780M。CPU 推理够用，核显可走 **ONNX Runtime DirectML / OpenVINO** 加速。**注意**：AMD 平台没有 CUDA，TensorRT 用不了 |

### 2.1 ⚠️ 你的最大技术风险：AMD 平台 + 操作系统

这是你方案里唯一需要提前决策的事：

| 方案 | 推理加速 | 优点 | 缺点 |
|---|---|---|---|
| **零刻 mini PC + Windows** | ONNX Runtime (DirectML) / OpenVINO | 驱动简单，D435i/OAK 官方支持好，海康 MVS 在 Win 上最稳 | DirectML 生态不如 CUDA；Windows 非实时内核，帧率抖动大 |
| **零刻 mini PC + Ubuntu** | ONNX Runtime (CPU/ROCm) | 系统稳定，实时性好，Docker 部署方便 | 海康 SDK 在 Linux 上要装 MVS for Linux；**ROCm 对 780M 核显支持很有限** |
| **换 NVIDIA 平台 (Jetson Orin Nano / 带独显的 mini PC)** | TensorRT | 生态无敌，社区代码 90% 是这条路 | 要花钱；Jetson 采购/散热/供电要额外设计 |

> **我的建议**：
> - 如果社团**能搞到一张 NVIDIA 卡或 Jetson Orin Nano**，优先换。不是为了算力，是为了**能抄社区代码 + TensorRT 的低延迟**，能省你至少 3 周。
> - 如果只能用 7840：**走 Windows + ONNX Runtime DirectML**，或者 Ubuntu + ONNX Runtime CPU（YOLO 输入 416×416 的情况下 CPU 也能到 200+ FPS）。
> - **不要**在这上面纠结超过一周。7840 跑传统视觉方案（灯条 + SVM/模板匹配）完全够用，**自瞄的第一版根本不需要深度学习**。

### 2.2 延迟预算（贴在显示器上）

自瞄系统的延迟预算，来自"相机曝光 → 弹丸出膛"：

```
相机曝光+读出      ~3-8 ms   （曝光 2ms + USB3 传输）
图像预处理+检测    ~3-8 ms
PnP + 坐标变换     ~0.5 ms
串口传输            ~1-2 ms  （115200 bps 下一帧 16 字节约 1.4ms）
电控接收+云台响应   ~5-15 ms （电机响应，主要项）
────────────────────────────
合计                ~15-40 ms
```

一个 30 m/s 的弹丸、目标以 3 m/s 横向移动，**20 ms 延迟 = 6 cm 偏差**。
在 5 m 距离上，小装甲板宽度才 ~15 cm。**所以延迟每省 10 ms 都是实打实的命中率。**

延时优化清单（按收益排序）：
1. 串口波特率从 115200 提到 **921600** 或 **1.5M**（和电控商量）
2. 相机曝光降到 **2~3 ms**，靠补光/大光圈保证亮度，不用高增益（高增益 = 噪点 = 检测抖动）
3. 检测算法**别做全图**，只在上一帧目标附近开 ROI（能省 60%+ 时间）
4. 关闭一切调试用的 `imshow`/`imwrite`，日志改成环形缓冲
5. 用 C++ 或 Python 但**避免逐帧创建大数组**，复用 buffer

## 3. 技术栈全景：上位机到底由哪些模块组成

```
┌──────────────────────────────────────────────────────────────────┐
│                       上位机程序（你的活）                        │
│                                                                  │
│  [1] 图像采集层                                                   │
│      海康SDK / V4L2 / DepthAI → cv::Mat                          │
│      关键：硬件时戳、曝光增益锁定、零拷贝                         │
│                          ↓                                        │
│  [2] 预处理层                                                     │
│      去畸变(remap) / 通道分离 / 二值化 / 亮度归一化                │
│      关键：预处理表预计算缓存，不要每帧重新计算                    │
│                          ↓                                        │
│  [3] 检测层            ← 你唯一熟悉的部分，但只占 20%              │
│      路线A 传统视觉：灯条配对 + 数字识别(SVM/模板)                 │
│      路线B 深度学习：YOLOv8/v11 检测4类装甲板 + 角点回归           │
│      关键：ROI 跟踪、置信度平滑、误检过滤                          │
│                          ↓                                        │
│  [4] 位姿解算层  ★核心难点                                        │
│      2D 角点 → solvePnP → 目标在相机系下的 (x,y,z) + 姿态          │
│      关键：装甲板物理尺寸、角点顺序、IPPE/SQPNP 的选择             │
│                          ↓                                        │
│  [5] 状态估计层  ★核心难点                                        │
│      卡尔曼滤波 / 扩展卡尔曼 / 跟踪器(IoU+匈牙利)                  │
│      输出：平滑后的角度、角速度、以及"目标是否可信"                │
│      关键：反小陀螺靠这里估计 ω，不是靠检测                        │
│                          ↓                                        │
│  [6] 坐标变换层  ★核心难点                                        │
│      相机系 → 云台系 → 枪口系                                     │
│      关键：手眼标定，旋转矩阵 + 平移向量的准确性                   │
│                          ↓                                        │
│  [7] 弹道解算层  ★核心难点                                        │
│      已知初速 + 重力 → 反解 pitch 补偿角                          │
│      关键：弹速必须实测；迭代 3~5 次收敛                          │
│                          ↓                                        │
│  [8] 通信层                                                       │
│      组帧 → 校验 → 串口发送 (100~1000 Hz)                         │
│      关键：协议要电控签字；要处理掉线重连、开机时序                │
│                                                                  │
│  [9] 横切关注点：多线程/时戳同步/日志/参数热加载/看门狗/录包回放    │

```

每一层都会在下面第 5 章的路线里变成可执行的学习任务。

## 4. 串口协议：你现在就可以发给电控同学

**这是你能立刻推进、且最能体现专业度的事。** 不要等代码写完才谈协议——协议是接口，先定死。

### 4.1 推荐协议（视觉 → 电控）

```c
// 帧格式：小端序 (Little Endian)
// 总长 22 字节
#pragma pack(push, 1)
typedef struct {
    uint8_t  sof;          // 0x5A  帧头
    uint8_t  mode;         // 0x00=空闲 0x01=自瞄 0x02=打符 0x03=校准 0xFF=错误
    float    yaw;          // 目标相对云台的偏航角 (度, 右正)
    float    pitch;        // 目标相对云台的俯仰角 (度, 上正)
    float    distance;     // 目标距离 (米)
    uint16_t seq;          // 帧序号，每帧+1，用于丢帧统计
    uint8_t  confidence;   // 0-255 置信度，电控可据此设置开火门限
    uint8_t  checksum;     // 前 20 字节逐字节异或
} VisionToGimbal_t;        // sizeof == 22
#pragma pack(pop)
```

### 4.2 电控 → 视觉（回传，仅方案 B/C 需要）

```c
#pragma pack(push, 1)
typedef struct {
    uint8_t  sof;          // 0xA5
    float    gimbal_yaw;   // 云台当前 yaw (度)，IMU 或编码器值
    float    gimbal_pitch; // 云台当前 pitch (度)
    uint8_t  bullet_speed; // 实测弹速 (m/s)，0 表示未测到
    uint8_t  game_state;   // 比赛阶段/血量等标志位
    uint8_t  checksum;
} GimbalToVision_t;
#pragma pack(pop)
```

### 4.3 必须和电控确认的 6 个问题（打勾式）

- [ ] 波特率：115200 / 460800 / **921600** / 1500000，用哪个？
- [ ] 发送频率：建议 **200~500 Hz**（不是越高越好，超过电控处理能力反而堵塞）
- [ ] 角度定义与正负号：**yaw 右转为正**？**pitch 上抬为正**？在哪校准到零位？
- [ ] 单位：角度用**度**还是**弧度**？（协议写死，别两边各自假设）
- [ ] 丢失处理：连续 N 帧没收到，云台应该保持还是回中还是断电？
- [ ] 开机时序：电控先开还是视觉先开？视觉程序崩了电控怎么知道？

> **踩坑预警**：`float` 的大小端和 `#pragma pack` 对齐，是视觉-电控联调第一大杀手。
> **第一次联调务必先发一组固定值**（比如 yaw=1.0, pitch=2.0, distance=3.0）让电控用示波器/串口助手读出 `1.000 / 2.000 / 3.000`，确认无误再传真实数据。

### 4.4 联调前自测脚本（你写完协议后第一件事）

```python
import struct

def pack(yaw, pitch, dist, seq, mode=1, conf=200):
    body = struct.pack('<BBfffHB', 0x5A, mode, yaw, pitch, dist, seq, conf)
    checksum = 0
    for b in body:
        checksum ^= b
    return body + bytes([checksum])

if __name__ == '__main__':
    frame = pack(1.0, 2.0, 3.0, 0)
    print(f'len={len(frame)} (should be 22)')
    print(frame.hex(' '))
    # 期望：5a 01 0000803f 00000040 00004040 0000 c8 xx
```

## 5. 90 天学习路线

假设你每周能投入 15~20 小时。**每阶段都有验收标准，过不了不许进下一阶段。**

### 阶段 0（第 1 周）：把地基砸实，别急着写检测

| 主题 | 具体学什么 | 验收标准 |
|---|---|---|
| **C++ 基础** | 类/引用/智能指针/`std::chrono`/编译链接。不用精通，够写工程即可 | 能独立用 CMake 编译一个链接 OpenCV 的多文件程序 |
| **Linux 或 Windows 开发环境** | 选一个定下来。CMake、git、gdb/VS 调试 | `git log` 能看出你每天在干活 |
| **相机模型** | 针孔模型、内参矩阵 K、畸变系数、`cv::calibrateCamera` | 能解释 K 里每个参数是什么，为什么要标定 |

**关键动作**：拿棋盘格（或打印的 ChArUco/AprilTag 板）**现在就把海康相机的内参标出来**。
- 采 30~50 张不同角度/距离的图
- 重投影误差（RMS）**< 0.3 px** 才算合格
- 标定结果存成 YAML，别每次重新标

> 为什么这周就要做：标定是一次性的脏活，但它是一切精度的源头。用 USB 摄像头标完再换工业相机 = 白标一次。

### 阶段 1（第 2~3 周）：传统视觉检测装甲板

**别一上手就训练 YOLO。** 先用传统方法跑通，你会真正理解"什么是装甲板"。

| 主题 | 具体学什么 |
|---|---|
| 颜色空间 | BGR / HSV / **Lab**；RM 灯条是红/蓝发光体，Lab 或 HSV 阈值更稳 |
| 形态学 | 膨胀腐蚀、开闭运算去噪 |
| 轮廓分析 | `findContours`、`minAreaRect`、长宽比/面积/角度筛选 |
| **灯条配对** | 两个灯条：长宽比匹配、平行度、中心连线与灯条垂直、间距比例 |
| 数字识别 | 装甲板上的数字（1/2/3/4/5/基地/前哨站）。**模板匹配或 SVM**，别上 CNN |
| 装甲板类别 | 小装甲板(步兵)、大装甲板(英雄/基地)、前哨站……**尺寸以你队规则手册为准** |

**验收标准**：
- 用 USB 摄像头对着手机播放的比赛录像，能稳定框出装甲板，**误检率可接受**（背景灯、观众席灯是主要干扰源）
- 能输出 4 个角点的**有序**坐标（左上→右上→右下→左下，顺序错 = PnP 结果全错）

### 阶段 2（第 4~5 周）：PnP 与坐标变换 ★难点一

| 主题 | 具体学什么 |
|---|---|
| 旋转表示 | 旋转矩阵 ↔ 欧拉角 ↔ 四元数 ↔ 轴角，`cv::Rodrigues` |
| **solvePnP** | 输入：装甲板 3D 物理角点 + 图像 2D 角点 + 内参。输出：rvec, tvec |
| PnP 求解器选择 | `SOLVEPNP_IPPE_SQUARE`（正方形靶首选）、`SOLVEPNP_ITERATIVE`、`SQPNP`；**对比精度** |
| 手眼标定 | 相机→云台→枪口 的旋转 R 和平移 t。用 `cv::calibrateHandEye` 或手算 |
| 坐标变换链 | `p_gimbal = R_c2g * p_cam + t_c2g`，然后转成 yaw/pitch |

**验收标准**：
- 已知距离放装甲板（比如 5.000 m），PnP 解出的 z **误差 < 3 cm**
- 转成角度后，与量角器/激光笔实测角度**误差 < 0.5°**
- 理解并能口述：为什么直接用 `atan2` 从像素算角度是错的（答案是畸变 + 光心不在图像中心 + 需要 3D 姿态）

### 阶段 3（第 6~7 周）：深度学习检测 + 部署（你的已有技能终于派上用场）

| 主题 | 具体学什么 |
|---|---|
| 数据集 | 自己采：真车录像 + 屏幕翻拍 + 不同光照/距离。**标注 4 类装甲板 + 数字** |
| 数据增强 | 亮度/对比度抖动、运动模糊、马赛克。**运动模糊必须做**，这是实车最大难点 |
| 模型 | YOLOv8n / YOLO11n（追求速度）或 YOLOv8s（平衡）。输入 416×416 或 640×640 |
| 训练 | 云端 GPU（Colab/学校服务器）或社团有卡的机器。**别用 7840 训练** |
| **导出与部署** | `.pt` → **ONNX** → ONNX Runtime / OpenVINO / TensorRT。重点学 **INT8/FP16 量化 + 前后处理对齐** |
| 前后处理 | letterbox 缩放、NMS、坐标反映射回原图。**量化后精度掉了要会定位** |

**验收标准**：
- ONNX 模型在你的 7840 上推理 **> 100 FPS**（416×416）
- 检测帧率在实车录像上稳定，**不出现逐帧抖动**
- **必须保留传统视觉作为兜底**：深度学习漏检时用传统方法补，或者比赛现场两个可切换

> **重要判断**：如果阶段 1 的传统视觉在你队场地上已经够稳（帧率 200+，误检可接受），**阶段 3 可以延后甚至跳过**。深度学习带来的收益，常常小于它在量化、部署、调试上吃掉的时间。**能打中人的方案就是好方案。**

### 阶段 4（第 8~9 周）：状态估计、弹道解算、反小陀螺 ★难点二

| 主题 | 具体学什么 |
|---|---|
| 滤波基础 | 卡尔曼滤波（KF）、扩展卡尔曼（EKF）、`alpha-beta` 滤波。看 B 站/《概率机器人》前几章 |
| 目标跟踪 | 帧间关联（IoU + 匈牙利算法）、多目标 ID 保持、遮挡处理 |
| 延迟补偿 | 记录"图像采集时戳"，用估计的角速度外推 **当前时刻** 的目标位置 |
| **弹道解算** | 斜抛运动 + 重力补偿。给定水平距离 x、高度差 h、初速 v₀，反解 pitch 角。**迭代求解**，考虑空气阻力 |
| **反小陀螺** | 目标绕自身 z 轴旋转时，装甲板在半径为 r 的圆上运动。用检测到的角度序列估计 **ω 和相位 φ**，预测未来时刻的装甲板角度 |
| 开火决策 | 什么时候允许开火：角度误差 < 阈值 且 持续时间 > 阈值 且 置信度 > 阈值 |

**弹道解算的最小代码骨架**：

```python
import math

def solve_pitch(horizontal_dist, height_diff, v0, g=9.8, iters=8):
    """反解俯仰角，含重力补偿。返回弧度。"""
    pitch = math.atan2(height_diff, horizontal_dist)  # 直线瞄准作为初值
    for _ in range(iters):
        t = horizontal_dist / (v0 * math.cos(pitch))
        # 需要的出射角，使弹丸在时间 t 后到达目标高度
        target = height_diff + 0.5 * g * t * t
        pitch = math.atan2(target, horizontal_dist)
    return pitch
```

**验收标准**：
- 静态靶：3 m / 5 m / 8 m 三个距离，实测偏差曲线，**8 m 内命中率 > 70%**
- 移动靶（横向 2 m/s）：能打中，且**提前量方向正确**
- 反小陀螺：目标以 ~2 rad/s 自转时，**命中率明显高于不做预测的版本**（用数据说话，别凭感觉）

### 阶段 5（第 10~12 周）：系统工程化 + 实车联调

| 主题 | 具体内容 |
|---|---|
| 多线程架构 | 采集线程 / 推理线程 / 通信线程，**无锁队列或双缓冲**传递数据 |
| 时戳同步 | 每帧图像带采集时戳，贯穿到发送时刻，全链路可追踪 |
| 参数热加载 | YAML 配置文件 + 运行时重载，**改参数不用重启程序**（现场调试救命） |
| 录包回放 | 把相机帧 + 时戳录成文件，离线反复调试算法。**这是效率放大器** |
| 看门狗 | 程序卡死自动重启；串口掉线自动重连 |
| 稳定性 | 连续跑 30 分钟不崩溃、不泄漏内存、帧率不衰减 |

**验收标准**：
- **实车打靶**：静止靶命中率 > 70%，移动靶 > 40%
- 连续运行 30 分钟无异常
- 你能在 30 分钟内把整套系统部署到一台干净的新机器上

## 6. 常见坑清单（联调前必读）

| # | 坑 | 症状 | 解法 |
|---|---|---|---|
| 1 | **角点顺序错** | 云台朝反方向转 / 距离正负反了 | 固定角点顺序，写单测。用 Debug 画出角点编号 |
| 2 | **串口字节对齐** | 电控读到的数是天文数字 | `#pragma pack(1)`，双方都加；先发固定值验证 |
| 3 | **大小端不一致** | 数值完全乱 | 协议写死小端，用 `struct.pack('<...')` |
| 4 | **角度单位混用** | 云台猛甩 | 协议里写死"度" |
| 5 | **自动曝光/自动增益** | 帧率抖动、检测忽好忽坏 | 相机全部手动模式，曝光锁 2~3 ms |
| 6 | **卷帘快门** | 转云台时图像歪斜 | 用全局快门的工业相机 |
| 7 | **镜头畸变未校正** | 图像边缘目标测距偏大 | `undistort`，且必须用**标定时的分辨率** |
| 8 | **云台-相机不同轴** | 近距离偏得少、远距离偏得多（或反之） | 手眼标定，检查光轴与枪管平行度 |
| 9 | **弹速未实测** | 近距离准、远距离全空 | 让电控测速上报，或在弹道上放测速仪 |
| 10 | **高频串口丢帧** | 目标突然跳一下 | 加帧序号 + 校验；电控端做插值 |
| 11 | **调试输出拖慢帧率** | 上车正常、开调试就卡 | 日志异步写，或者编译期关掉 |
| 12 | **背景灯误检** | 观众席灯光被当成装甲板 | 颜色 + 形状 + 数字三重校验，加 ROI 限制 |
| 13 | **比赛场地光照突变** | 上场就失效 | 亮度归一化 / 自适应阈值；**赛前提前去场地调参数** |
| 14 | **开机时序** | 一上电就抽风，重启才好 | 视觉先持续发"空闲"帧，电控发现有效帧才切入自瞄 |
| 15 | **程序崩溃无提示** | 云台乱转 | 看门狗 + 电控端超时保护（超时回中/停止开火） |

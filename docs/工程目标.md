# 工程目标：高速 · 精准 · 稳（量化版）

> **优先级：稳 ＞ 精准 ＞ 高速。**
> 三者冲突时按此顺序取舍，**不现场讨论**。
>
> 本文件把"高速精准稳"从口号变成**可测量、可验收**的指标。
> 来源：队伍负责人明确要求（2026-10-07）：
> "把工程级，和追求高速精准稳也固化"

---

## 0. 为什么必须有优先级

三者在本项目里**真实冲突**，举例：

| 冲突 | 高速想要 | 精准想要 | 稳想要 | 按优先级取 |
|---|---|---|---|---|
| 推理频率 | 每 5 ms 推理一次 | — | 抖动小、预留余量 | **稳**：固定 20 ms 周期，留 300x 余量 |
| 模型大小 | 大网络更准 | 大网络更准 | 小网络更快更不容易崩 | **稳 > 精准 > 高速**：用够准的最小网络 |
| 目标选择 | 立刻切目标 | 确认后再切 | 避免抖动 | **精准 + 稳**：加确认窗口 |
| 开火策略 | 见敌就打 | 瞄准在环内才打 | 避免热量锁定 | **稳**：热量留 15% 余量 |
| 降级时机 | 尽量不降级 | — | 宁可误降 | **稳**：宁可误降 |

**一句话**：**宁可慢一点、宁可保守一点，也要稳。**

---

## 1. 稳（可靠性）—— 最高优先级

### 1.1 硬指标

| 指标 | 目标 | 当前实测 | 验收方式 |
|---|---|---|---|
| **控制周期抖动** | P99 ≤ 2× 标称周期 | 待测 | 长时日志统计 |
| **推理延迟** | P99 ≤ 10 ms | **30.7 µs**（余量 300x） | `export_onnx.py` 基准 |
| **连续运行无劣化** | ≥ 1 小时，延迟/内存无上升趋势 | 待测 | 长时稳定性测试 |
| **降级触发成功率** | 100%（人为注入故障必触发） | 待测 | 降级演练脚本 |
| **降级后仍能行动** | 100% | 待测 | 降级演练脚本 |
| **单点故障数** | 0（任何单点失效不导致整车不可用） | 待审计 | 依赖图审查 |
| **崩溃恢复** | 进程崩溃后 ≤ 2 s 恢复，期间走规则层 | 待测 | 杀进程演练 |

### 1.2 设计约束（来自 `工程红线.md`）
- 三层兜底：RL → 规则 → 最低安全策略，每层**独立可运行**
- 切换**全自动**，判定**宁保守勿激进**
- **RL 永不独占控制权**，只输出建议，由仲裁采纳

### 1.3 绝对禁止
- ❌ 依赖赛场网络
- ❌ 比赛中改代码 / 现场调参
- ❌ 未演练过的兜底（等于没有兜底）
- ❌ 任何"只有我知道怎么恢复"的状态

## 2. 精准（准确性）—— 次高优先级

### 2.1 决策精准

| 指标 | 目标 | 当前 | 说明 |
|---|---|---|---|
| **占点率** | ≥ 0.90 | 规则基线 **1.000** ✅ / RL **0.002** ❌ | 2026 胜负只由占点与战亡决定 |
| **净胜点**（vs 规则基线） | > 0 | 待重训 | 低于基线就没有理由用 RL |
| **胜率**（同 EVAL_SEED） | ≥ 规则基线 | 待重测 | 固定 `EVAL_SEED=20261007` |
| **位置时间集中度** | ≥ 0.80（好哨兵实测 81.4%） | 待测 | 见 `参考卡.md` §2.4 |

### 2.2 工程精准

| 指标 | 目标 | 当前 | 验收方式 |
|---|---|---|---|
| **ONNX vs PyTorch 数值误差** | < 1e-4 | **1.79e-07** ✅ | `export_onnx.py` |
| **训练/推理口径一致** | 逐位一致 | ⚠️ 未做（门控仍在 C++ 侧） | 把 argmax/softmax 烤进图 |
| **规则一致性** | 100% | **95/95** ✅ | `rules_test.py` |
| **训练前体检** | 100% | **31/31** ✅ | `preflight.py` |
| **输入边界** | 极端输入不产生非法动作 | 待补 | 注入 NaN/越界测试 |

### 2.3 精准的判据
**"精准"不是"训练 loss 小"，而是"闭环对局里赢"** —— 离线指标已被证明不可信
（见 `参考卡.md` §2.3：RMUC-OfflineRL 的 BC/DT 增益几乎全是估计器偏差）。

## 3. 高速（性能）—— 第三优先级（够用即可）

### 3.1 车端（部署）—— 这是比赛真正相关的

| 指标 | 目标 | 当前实测 | 余量 |
|---|---|---|---|
| **单次推理** | ≤ 5 ms | **30.7 µs** | 163x |
| **推理频率** | ≥ 50 Hz | 可支持 **32.5 kHz** | 充足 |
| **CPU 占用** | ≤ 50%（单核） | 待测 | — |
| **内存占用** | ≤ 200 MB | 待测 | — |
| **冷启动到就绪** | ≤ 10 s | 待测 | — |

**判据：车端只要能跟上控制周期就算达标，不追求更快。** 因为"稳"优先于"高速"。

### 3.2 训练端（本机）—— 只影响迭代速度

| 指标 | 当前实测 |
|---|---|
| 向量环境吞吐 | **511k 步/秒**（4000 环境） |
| 环境+策略吞吐 | 346k（GPU）/ ~200k（CPU，4096 环境） |
| 完整训练吞吐 | **~40k 步/秒**（512×64 GPU） |

**注意**：训练慢只让迭代慢，**不影响比赛成绩**。不要在赛前为了提速重构训练代码。

## 4. 冲突仲裁表（现场直接用，不讨论）

| 场景 | 处理 |
|---|---|
| 延迟略超预算，但策略更准 | **降频不降准**：保持 20 ms 周期，允许多步不推理 |
| 规则层与 RL 层结论冲突 | **听规则层**（稳优先） |
| 视觉目标抖动导致频繁切目标 | **加迟滞**（连续 N 帧一致才切） |
| 热量接近上限但目标出现 | **停火**优先（避免锁定 = 更长时间的失效） |
| 内存/延迟出现上升趋势 | **立即降级到规则层**并告警，不等待确认 |
| 不确定该不该降级 | **降** |

## 6. 验收门槛（"能不能上场"的量化版）

**必须全部满足，缺一不可：**

- [ ] `rules_test.py` 100% 通过
- [ ] `preflight.py` 100% 通过
- [ ] 闭环净胜点 ≥ 规则基线（同 `EVAL_SEED`）
- [ ] ONNX 数值误差 < 1e-4 且口径一致
- [ ] 连续运行 1 小时无劣化
- [ ] **降级演练通过**（注入故障必触发、降级后仍能行动）
- [ ] 断电重启能自动恢复到可打状态
- [ ] 遥控器接管可用
- [ ] 车端离线可装
- [ ] 版本号已冻结并记录

**任一不满足 = 不能上场。** 比赛宁可用规则基线，也不用未验收的 RL。

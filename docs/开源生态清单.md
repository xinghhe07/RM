## 0. 先说一条改变判断的发现

**2026 赛季的哨兵是「轮腿 / 地面自由移动」，不是滑轨。** 证据：

- 浙大 Hello World 战队仓库描述原文：**"26赛季轮腿哨兵导航"**
- 现有哨兵仿真项目全都是 **Nav2 + SLAM + 点云**（Livox MID360 / Fast-LIO）

**这意味着**：哨兵导航类开源对你的项目**直接可用**（而不是像滑轨那样无关）。
之前我把"导航执行器"列为可选，现在应升级为**必接**：
RL 只输出子目标点，把 Nav2 当执行器 —— 这也是把 RL 风险限制在决策层的最省力做法。

## 6. 通用 RL 框架（本项目自研环境，仅作对照）

**硬结论：没有任何框架同时原生支持「动作掩码 + 混合动作」。**

关键反证：[sb3-contrib `MaskablePPO` 文档](https://sb3-contrib.readthedocs.io/en/master/modules/ppo_mask.html) 的 "Can I use?" 表明确写着 **Box ❌ / Dict ❌** —— 它**连连续动作都不支持**。
所以"MaskablePPO + 自定义 Dict head"在类继承层面就不通。

| 框架 | ⭐ | License | 混合动作 | 掩码 |
|---|---|---|---|---|
| [CleanRL](https://github.com/vwxyzjn/cleanrl) | **10,501** | MIT（API 报 NOASSERTION） | ❌ | ❌（作者代码在[独立仓库](https://github.com/vwxyzjn/invalid-action-masking)） |
| [SB3](https://github.com/DLR-RM/stable-baselines3) | 13,871 | MIT | ❌ | ❌ |
| [sb3-contrib](https://github.com/Stable-Baselines-Team/stable-baselines3-contrib) | 739 | MIT | ❌ | ✅ |
| [TorchRL](https://github.com/pytorch/rl) | 3,592 | MIT | ✅ TensorDict | ✅ **原生** `MaskedCategorical` |
| [RLlib](https://github.com/ray-project/ray) | 43,977 | Apache-2.0 | 需自定义 | 有示例 |
| [ml-agents](https://github.com/Unity-Technologies/ml-agents) | 19,720 | Unity 自有 | ✅ | ✅ | （但要求环境在 Unity） |
| [Sample-Factory](https://github.com/alex-petrenko/sample-factory) | 1,026 | MIT | ❌ | ❌（自博弈强项） |
| [PettingZoo](https://github.com/Farama-Foundation/PettingZoo) | 3,526 | MIT | 取决于训练库 | 只是环境 API，**做对手池合适** |

**结论**：自建 2D 环境 + 混合动作 + 掩码 + 自博弈，**继续自己写 PPO 性价比最高**。
迁到任何框架都要重写 policy head + buffer + 分布，收益接近 0。

**PPO 稳定性权威依据**（我这轮踩坑全靠它修好）：
[PPO 原文](https://arxiv.org/abs/1707.06347)、[Spinning Up](https://spinningup.openai.com/en/latest/algorithms/ppo.html)（"clip 不是硬约束，我们靠 early stopping"）、
[ICLR 2022《37 个实现细节》](https://iclr-blog-track.github.io/2022/03/25/ppo-implementation-details/)（detail 7 = per-minibatch 优势归一化）、
[What Matters in On-Policy RL](https://arxiv.org/abs/2006.05990)、[SB3 PPO 文档](https://stable-baselines3.readthedocs.io/en/master/modules/ppo.html)（`clip_range_vf` 依赖奖励尺度）、
[Schulman KL 估计器](http://joschu.net/blog/kl-approx.html)

## 8. 我三轮调研的净结论

### 8.1 空白区（三轮独立检索均未找到）

1. **"比赛规则 + 裁判系统 + Gym 接口 + 可并行"的 RL 就绪仿真器** —— 不存在
2. **"占点扣对方胜利点"机制的 RL 论文或开源** —— 不存在
3. **混合动作空间（连续+离散多头）RL 策略部署的现成框架** —— 不存在
4. **处理"hold position/驻留"奖励的专门论文** —— 不存在
5. **任何"哨兵 RL 在正式比赛击败人类队伍"的可验证成绩** —— 不存在

> RMUC-OfflineRL 作者原话印证了第 1 条：
> *"没有能支撑强化学习训练的仿真平台：现有模拟器均未开放裁判系统数据级别的接口，且无法并行训练。"*

### 8.2 但要修正我前两轮的一个判断

**我说过"哨兵 + RL 完全没有前人"—— 这不准确。** 实际存在多个**同题或近题**项目：

- **2D 哨兵决策训练环境**（MIT，RMUL2024 规则）
- **RMUC 2026 pygame 模拟器**（自述用于测试哨兵决策）
- **3v3 哨兵导航 + Gazebo 仿真**
- **RMUL 哨兵决策**（MIT）
- **哨兵云台 RL**（Apache-2.0）

它们**都不完整**（规则过时 / 无 license / 只做子问题），所以你的环境仍有价值，
但**你应该先花两小时把这几个读一遍** —— 至少能避免重复造轮子，并知道别人栽在哪。

### 8.3 最短路径建议

**并行两条**：

| 路线 | 做什么 | 依据 |
|---|---|---|
| **A. 自建环境（主线，进行中）** | 以本项目为核心；参考 2D 哨兵环境（MIT）+ RMUC-OfflineRL 的奖励设计 | 唯一能覆盖 2026 占点机制的方案 |
| **B. 接入现成执行器** | RL 只输出子目标点 → 交给 `pb2025_sentry_nav`（444★, Apache-2.0）/ Nav2 | 把 RL 风险限制在决策层，最省力 |
| **C. 3D 交叉验证** | 把 rmul_2026 场地 + 哨兵模型补进 `rmu_gazebo_simulator` 做规则一致性验证 | 需自己补场地/哨兵/headless 并行 |

**立刻要做的三件事**：
1. 读 `Chen20040604/2D-sentry-decisionTrainingEnv-simulator`（MIT，同题 2D 环境）
2. 读 `ezthor/rm-battlescope` 的两份 docs（决定数据集能不能用）
3. 精读哈工大(威海) HERO 的 RM2026 哨兵技术报告（BBS，S 级评审）

## 1. 规则基线：2026 到底怎么打

⚠️ **这一节的所有数值都来自官方手册原文**（`C:\RM\rules\rules_text\` 下有抽取好的文本可查证）。
**2025 与 2026 的哨兵不是同一台机器**，网上大量教程和开源代码还是 2025 版，直接抄会错。

### 1.1 2026 vs 2025 哨兵关键差异

| 项 | 2025 V1.1.1 | **2026 V1.2.0（你们的）** |
|---|---|---|
| 发射机构 | 2 个 17mm | **1 个 17mm** |
| 射击热量上限 | 400 | **260** |
| 热量冷却速率 | 80/秒 | **30/秒** |
| **持续射速上限** | 8 发/秒 | **3 发/秒** |
| 17mm 单发伤害 | 10 | **20** |
| 初始允许发弹量 | 750 | 750 |
| 血量 / 底盘功率 / 初速上限 | 400 / 100W / 25m/s | 同 |
| 增益点名称 | 中心增益点 | **控制区** |

> **射速这一栏决定了哨兵的战术性格。** 2026 是 1 管 260 热量：满热连射只能打约 31 发
> （≈1.6 秒）就超限锁定，然后要**冷却到 0 才解锁**（约 8.7 秒）。也就是说哨兵是
> **"点射—长冷却"的节奏，而不是持续压制**。这个结论直接改变最优策略，且是环境实测出来的
> （见 `rules_test.py` 第 9 节：瞬时 20 发/秒，长期均值 2.88 ≈ 3 发/秒）。

### 1.2 胜利点机制（两赛季符号相反，最易出错）

| | 2025 §3.3.6 | **2026 §3.3.4** |
|---|---|---|
| 开局 | 双方 0 | **双方各 200** |
| 占增益点 | 我方 **+1**/秒 | **对方 −1**/秒 |
| 机器人战亡 | **对方 +20** | **自己 −20** |
| 获胜条件 | 先到 **200** | 一方归 **0**（或时间到比谁高） |

原文（2026 §3.3.4）：*"双方各有200 点胜利点……当一方机器人占领控制区时，对方每秒扣除1 点胜利点。每当一方机器人战亡，该方扣除20 点胜利点。"*

> **对策略的直接影响**：战亡不是"损失一次输出"，而是**直接送掉 20 秒的占点优势**。
> 一条命 = 20 点 = 对方占点 20 秒。所以"活得久"在 2026 里的权重大幅高于 2025。
> 奖励函数必须体现这一点，否则策略会学会"换命"。

### 1.3 其他关键约束

| 约束 | 内容 | 为什么重要 |
|---|---|---|
| **零人类干预** | "哨兵机器人需全自动运行，最多配置1 个遥控器用于调试"；R21 要求准备阶段后上交遥控器 | 从开局到结束全是你的程序在跑，没有"人接手"这回事 |
| **多机通信不允许** | 2026 表 3-4 | **哨兵拿不到任何敌方坐标**，也没有雷达兵种。观测必须完全建立在自身感知上 |
| 复活 | 读条复活，首次 10 进度、每次 +10，每秒 +2；复活后血量回 20%、无敌 10 秒；**哨兵复活后发射机构立即解锁** | 第 n 次战亡要等 5n 秒 |
| 过热锁定 | Q1 > Q0 锁定**直到 Q1 = 0**；Q1 > Q0+100 当局永久锁定 | 不是降到上限以下就解锁，是必须归零 |

## 2. MuJoCo 与仿真栈：结论

**装不装？已经装了，但重点是"不需要它"。**

"哨兵强化学习"是两个不同课题，工具链不一样：

| 课题 | 需要物理引擎吗 | 优先级 |
|---|---|---|
| **A. 战术决策层**（走位、选目标、开火门控、资源分配） | **不需要**。血量/热量/胜利点全是标量规则，2D 抽象仿真就够 | **主力方向** |
| **B. 底层控制层**（底盘闭环、云台随动、抗扰动） | 需要 | 低，除非队里 PID 调不动 |

RM 哨兵的差距在 A 不在 B。**而 A 根本用不上 MuJoCo。**

**MuJoCo 的正确定位**：两天内跑通、理解连续控制、以后读论文代码时看得懂。**然后就停手。**

**坑 C：RTX 50 系（Blackwell / sm_120）的驱动。**

若 `nvidia-smi` 报错或看不到显卡，参考：
[Driver 555+ Setup for Blackwell GPUs on Ubuntu 22.04](https://gigagpu.com/nvidia-driver-555-blackwell-setup-ubuntu/)

> 注意：**这不阻塞你的开发。** 2D 环境在 CPU 上实测 21 万步/秒，没有 GPU 也能正常推进。

#### 从 Windows 拷贝项目到 Ubuntu 时的两个注意点

1. **shell 脚本必须是 LF 行尾。** 若 git 的 `core.autocrlf=true`（Windows 默认），
   `setup_env.sh` 会被检出成 CRLF，在 Ubuntu 上直接报
   `bash: ./setup_env.sh: /bin/bash^M: bad interpreter`。
   已在仓库里放 `.gitattributes` 强制 `*.sh` 用 LF 兜底；
   若手工拷贝，用 `file setup_env.sh` 确认，必要时 `sed -i 's/\r$//' setup_env.sh`。

2. **Python 文件默认编码。** Ubuntu 上是 UTF-8，Windows 上是 cp1252；
   本项目所有源码**只含 ASCII**，且读写文件都显式指定了 `encoding="utf-8"`，所以无风险。

> **已验证**：`setup_env.sh` 语法通过（`bash -n`）、纯 LF 行尾、参数分支行为正确
> （未知参数退 2 / `--check` 缺 venv 退 1 / 驱动检测正常）。
> **未验证**：真正的 Linux 路径语义与 apt 依赖 —— 那需要一台真 Ubuntu 才能跑。
> 本机装了 Git for Windows 的 bash 做过部分验证，但 Git Bash 里的 `python` 仍是
> Windows 版，输出 Windows 路径，所以**它不能替代真 Ubuntu 验证**。这点不夸大。

### 2.3 ⚠️ 已经踩过的环境坑（别再犯）
**坑 1：不要用 `conda create --clone`。**

我最初用 `conda create -n rl --clone d2l` 来复用 torch，结果把 `d2l` 的**全部已装包**
复制了过来 —— 共 139 个包，其中 `jupyter`/`notebook`/`nbconvert`/`ipython`/`torchvision`
/`d2l` 教学包等 **45 个与本项目完全无关**。

更麻烦的是：这些包自带的**依赖声明**会在你装别的东西时被 pip 拿来解算，于是出现
"装 onnxruntime 顺手把 numpy 从 1.23.5 升到 2.4.6，进而破坏 scipy"这种事。
依赖图脏了之后，`pip check` 会一直报一堆与你无关的冲突，掩盖真正的问题。

**正确做法**：新建空环境，只装 `torch cu128 + gymnasium + mujoco + numpy`。
清理后从 139 个包降到 **94 个**，`pip check` 只剩一条良性告警。

**坑 2：`onnxscript` 会把 numpy 顶到 2.x。**

导出 ONNX 需要 `onnxscript`，它经 `ml-dtypes` 依赖 `numpy>=2.0`，而 `scipy` 要求
`numpy<1.27`。解法：装完 ONNX 工具链后**把 numpy 钉回 1.26.4**（已实测 onnxruntime
在该版本下工作正常）。搭建脚本里 `-WithOnnx` 分支已自动处理。

**坑 3：RTX 5070（Blackwell / sm_120）必须 CUDA 12.8 的 torch。**

`pip install torch` 默认会装成 cu126 或 CPU 版。必须显式指定：
`pip install torch --index-url https://download.pytorch.org/whl/cu128`

## 2.4 部署：车端只有 CPU 完全够用（实测数据）

这是本项目最关键的一条工程结论。**比赛机（AMD 7845HX 级别，只有 CPU）不需要 GPU。**

### 推理延迟实测（单样本，4 线程）

| 方式 | 单次前向 | 理论上限 | 说明 |
|---|---|---|---|
| PyTorch | ~80–160 µs | 6,000–12,500 Hz | 依赖 torch，车端要装约 2.5GB |
| **ONNX Runtime** | **30.5 µs** | **32,762 Hz** | **车端不需要装 torch** |

**对比：哨兵决策频率是 1–10 Hz。** 上面任一方式都有 **3–4 个数量级**的余量。
**车端算力从来不是这个项目的瓶颈。**

而且注意：网络很小（hidden=128 时仅 **22,282 个参数**）。实测 hidden 从 128 加到 512
（参数多 13 倍），单次前向只从 430 µs 变到 444 µs —— 说明**延迟几乎全是 Python/调度开销，
不是算力**。所以这也解释了为什么换 ONNX Runtime 能提速数倍：省的是框架开销，不是 FLOPs。

### 部署链路（已实现并验证）

```bash
python -m rm_sentry.export_onnx --run runs/smoke_cpu
```

这个脚本做三件事，**第三件最重要**：

1. 导出 `policy.pt` → `policy.onnx`（90.5 KB）
2. **逐项对齐验证 PyTorch 与 ONNX Runtime 的输出**（不通过就报错退出）
3. 实测两者 CPU 延迟

实测结果：

```
数值一致性（PyTorch vs ONNX Runtime）:
  move_mu        最大绝对误差 1.788e-07 ok
  move_logstd    最大绝对误差 0.000e+00 ok
  target_logits  最大绝对误差 2.980e-08 ok
  fire_logit     最大绝对误差 0.000e+00 ok
  value          最大绝对误差 2.980e-08 ok
  掩码生效检查: 目标1(应被禁) logit=-1e9, 目标2(应可用) logit=0.4  -> ok
一致性通过（最大误差 1.79e-07 < 1e-4）
CPU 延迟: PyTorch 80.1 us  ->  ONNX Runtime 30.5 us（提速 2.6x）
```

> **为什么要做一致性验证**：这是最高频的部署事故 —— 仿真里表现好，导出后行为不同，
> 而原因是归一化/前后处理/dtype 对不上。把它做成脚本里的硬断言，就能在导出当场发现。

### 训练放哪、部署放哪（推荐分工）

| 环节 | 机器 | 理由 |
|---|---|---|
| **训练 / 调参 / 实验** | 你的 Windows 游戏本（RTX 5070） | GPU 让大规模并行更顺；不占用实机 |
| **导出 + 数值验证** | 游戏本（CPU 即可） | 30 µs 级，随手就验完 |
| **上车跑策略** | 实机 AMD 7845HX（CPU） | 只做前向推理，ONNX Runtime，不装 torch |
| **ROS 2 集成 / 联调** | 需要用实机时再去（要排队） | Nav2、串口、裁判系统 |

**也就是说：整个开发闭环可以在你的 Windows 机器上完成，实机只在"最后联调"时才需要。
这正是你想要的效果，而且可行。** 实机那台 AMD 7845HX 因为要排队共用，就当作"验证环境"
而不是"开发环境"。

### 3.1 环境设计的三条硬约束

这三条不是可选项，是规则逼出来的：

1. **1 Hz 战术决策层**：输出"怎么动 / 打谁 / 是否开火"。云台、扳机、底盘控制交给电控和导航栈。
   **不划这条线，训练永远不收敛。**
2. **信息孤岛**：2026 多机通信不允许 ⇒ 观测里**绝对不能有敌方真值坐标**。
   已实现 FOV（120°）+ 感知距离（9m）+ 掩体遮挡 + 位置噪声 + 2% 漏检，
   并用动作掩码禁止选择不可见目标。
3. **奖励围绕胜利点**：2026 是"扣对方"而非"自己加分"。战亡代价必须显著（一次战亡 = 20 秒占点）。

### 3.2 用法

```bash

powershell -ExecutionPolicy Bypass -File setup_env.ps1            # 首次搭建
```

## 4. ⚠️ 最重要的一条工程原则

**RL 必须是"增量"，不能是"替换"。**

先确保队里有一版**能上场的脚本策略**（行为树/状态机），再让 RL 去打败它。理由：

- RL 训练失败的默认结果是什么都没有，而比赛日期不会延后
- 没有脚本基线，你无法判断 RL 是在进步还是原地打转
- 现场出问题时能一键切回脚本 = **你才敢在正式比赛里用 RL**

**现成可借的基线**（都是活跃维护、Apache-2.0）：

| 仓库 | 用途 |
|---|---|
| [pb2025_sentry_behavior](https://github.com/SMBU-PolarBear-Robotics-Team/pb2025_sentry_behavior) | 哨兵决策**行为树**（BehaviorTree.CPP），含裁判系统条件节点。**这就是你要打败的对照组** |
| [pb2025_sentry_nav](https://github.com/SMBU-PolarBear-Robotics-Team/pb2025_sentry_nav) | 哨兵导航 Sim2Real（Nav2 + point_lio + small_gicp），有 Docker 镜像。**RL 只输出子目标点，把 Nav2 当执行器** |

> **当前状态提醒**：你们队哨兵是"从零开始"，**脚本基线还没有**。
> 严格说，在基线存在之前，RL 的胜负无法判定。**这是排在最前面的风险。**

## 5. 生态现状（避免重复造轮子或踩坑）

**硬结论：RM 生态里不存在"比赛规则 + 裁判系统 + Gym 接口 + 可并行"的 RL 就绪仿真器。**

| 方案 | 实测状态 |
|---|---|
| `rmoss_gazebo` | ROS 2 Jazzy + Gazebo Harmonic，但只有 3 个插件，**无裁判系统仿真插件，无哨兵整车模型** |
| `rmu_gazebo_simulator`（SMBU） | **最实用的 Gazebo 底座**：有 rmuc_2025 世界 + 裁判系统 Web 端，但仍不是 Gym 风格，**单实例无并行** |
| `RoboRTS`（官方） | 为 ICRA AI Challenge 设计，ROS 1，**已停更约 4.5 年** |
| `RMUC-OfflineRL` | 基于官方 613 局数据的离线 RL 框架。**没有闭环仿真分支**，其 README 把闭环列为"尚未完成" |
| 哨兵开源生态 | 清一色**行为树/状态机 + Nav2**。论坛上**没有任何"哨兵 + 强化学习"的成题开源** |

**你自己的 2D 环境就是当前最优解** —— 用 NumPy/PyTorch 写标量状态博弈，比 Isaac Lab 单卡
还快、还便宜，域随机化与奖励塑形改起来极方便。

### 5.1 官方数据集（值得单独说）

RM 官方在 2026-07 开源了 **RMUC 2026 区域赛数据**：**613 局、约 400 万条逐秒记录、1 Hz**。

几个**必须知道的坑**（不知道会得出错误结论）：
- `枪口朝向` 是 `atan2(dy,dx)` 零偏移，wrap 到 [−140, 220]；**`−140.0` 是"无云台数据"哨兵值**
- `events.目标robot_id` 对全部发弹与受击**均为 NULL** → 无法做逐机器人伤害归因 → 只能用队伍级奖励
- **数据中不存在视线/可见性字段**，坐标来自场地全局定位，不是机器人感知
- 顺便一句：该数据集是 **7v7（28×15m）** 场景，**不是 3v3**，观测/动作设计可参考但不能直接搬

| 1 | **用 2025 手册建模** | 热量/射速/伤害全错，胜利点符号相反 → 训练出反向策略 |

### 7.2 工程类（本项目调试中真实出现的 bug）

| # | 坑 | 症状 |
|---|---|---|
| 6 | **`reset()` 没复位热量锁定状态** | `auto_reset` 让新一局带着上一局的锁定开局，**直接污染训练数据** |
| 7 | **动作掩码与可见性错位一格** | 不可见目标在掩码里"可用"，可见的反而被禁 |
| 8 | **`step()` 取目标可见性时把自机槽当敌人** | 与掩码用的索引不一致，行为矛盾 |
| 9 | **对手开火没有冷却** | 每 0.1s 一发（100 dps），比哨兵自身输出还高，教出错误策略 |
| 10 | **张量里的"幽灵槽"** | `enemies` 槽 0 是自机槽；写 `enemies[:,0]` 改的是它而不是敌人 0 —— **静默出错** |
| 11 | 布尔张量原地 `&=` + 广播 | 出现过"部分列未被写入"，改用 `torch.logical_and` |
| 12 | 时间步与锁定阈值混叠 | dt=0.1 时射速只有 6.0 而非 8.0；dt=0.05 才对 |
| 13 | 测试用种子不隔离随机性 | 观测有随机漏检，逐帧可见性断言本身就不确定 |

### 7.2b ⚠️ 一类反复出现的 bug：跨 episode 状态未复位（已犯三次）

**这一类 bug 每次都造成训练退化，而且都很隐蔽。** 单独列出来，因为它是本项目
最贵的坑。

| 次 | 状态 | 未复位的后果 |
|---|---|---|
| 1 | `_lock1/_lock2/_holder/_grace`（热量锁定、控制区归属） | 新一局带着上一局的锁定开局，直接污染训练数据 |
| 2 | `_prev_vp_adv`（上一局 VP 基准） | 首个 step 的 `advance` 出现巨大尖峰 |
| 3 | `_dist_valid`（接近塑形的历史距离） | **每局重生白送 +1.0 奖励** —— 比占点一整步(+0.1)大一个量级，**策略学会"死掉刷重生奖励"** |

**规律**：任何"跨 step 累积/差分"的状态，在 `auto_reset` 时都必须处理。
**检查方法**：对每个 `self._xxx` 的跨步状态，问一句"新一局开始时它还合法吗？"

**诊断手法（可复用）**：构造"强制死亡 → auto_reset → 看下一步奖励"的测试，
断言该步奖励不应超过正常量级。这类尖峰靠看训练曲线是发现不了的。

### 7.2c ⚠️ 读错指标浪费的轮次（教训）

| 坑 | 说明 |
|---|---|
| **"伤害塌缩"是假的** | 训练日志里的 `dmg_out` 来自会在 `auto_reset` 归零的字段，看起来"634 → 4 塌缩"。换成"当前存活环境的平均累计值"后伤害一路稳涨到 612。**为一个不存在的现象追了好几轮** |
| **`--log` 验证不到 `launch()` 路径** | 脚本 `--log` 会提前 `return 0`，所以"漏 `import mujoco.viewer`"这种 bug 测不出来。**验证必须覆盖真正会执行的那条分支** |

### 7.3 部署类

| # | 坑 | 解法 |
|---|---|---|
| 14 | 训练用真值观测，实车只有带噪声感知 | 观测必须注入噪声、延迟、丢帧（已实现） |

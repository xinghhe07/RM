## 3. 历史教训：一次真实的阈值翻车（必须保留）

`开源借鉴.md §0.1` 记录：照抄 pb2025 的 `hp_min=200`（上限 400 的 50%）→ 本项目**开火率掉到 5.7%、占点率腰斩、净胜点 −78 → −103**。

**当时的归因**："本项目复活血量只有 80，阈值 200 比复活血量还高，于是复活即撤退。"

**本轮修正后的归因**：真因是**我们把官方回血机制关掉了**（`rmul_3v3_env.py: heal_supply_per_s = 0.0`）。官方 2026 规则 §3.3.2.1：

> 英雄、步兵、哨兵机器人占领己方补给区时，可以以每秒 **25% 上限血量**的速度回血。

哨兵上限 400 → **100 HP/s，4 秒回满**。pb2025 设 200 正是**因为能回血**，**场景其实是可比的**，是我们的**配置不可比**。

> **教训升级**：核对场景可比性时，不只要核对"阈值相对哪个量"，还要核对**"该机制在本项目是否被建模"**。
> 这条比原来的版本更强，写进本文档后续所有阈值设计。

## 4. 战术点图设计

### 4.1 数据模型（借鉴中科大 `nav_zone.hpp`，Apache-2.0）

三种几何原语 + 语义点 + 邻接边：

```python
# 借鉴：Walker152/navi_minco_bit  src/decision/bt_manager/include/bt_manager/utils/nav_zone.hpp
#   Area_Square / Area_Circle / AreaPolygon<N> 三种原语
#   其 contains() 为「边界含入 + 顶点安全交叉判定」，数值稳健，故沿用该算法思路
# 注：中科大原实现是 C++ 模板；本项目是 Python，重写为等价实现，并在单测里对齐边界行为。

class AreaSquare:   # 任意两对角点，自动归一化 min/max
class AreaCircle:   # 圆心 + 半径
class AreaPolygon:  # 顶点列表，射线法 point-in-polygon，边界含入
```

**语义点**（借鉴中科大 `PatrolPoint` + **哈工大 `Guard/Connector` 思想**，MIT）：

```python
@dataclass(frozen=True)
class TacticalPoint:
    pid: str            # 唯一 id，如 "ZONE_C"
    xy: tuple[float, float]   # 场地角点为原点的米坐标
    yaw: float = 0.0    # 建议朝向（弧度）；0 = +x
    kind: str = "guard" # guard(把守/驻守) | connector(通路/过点) | supply | home | observe
    dwell_ms: int = 0   # 到点后停留毫秒；0 = 不停留
    note: str = ""
```

**为什么带 `kind` 和邻接边**（对哈工大 PNG 范式的取舍）：
- 哈工大用"关键点 PNG + 拓扑图"（`GraphNode::NODE_TYPE{Guard=1, Connector=2}`，`occtopo2024low.png`），因为其场地 **30×18 m**、含桥洞/台阶/斜坡，关键点多到必须自动抽取。
- 我们 **12×8 m、点数约 12–16 个** → **手工表更好审**；且 PNG 是二进制，**没法 diff、没法 code review、没法单测**（本轮实测连 `web_fetch` 都取不到它）。
- **但采纳它的"图"思想**：中科大的 `nav_points` 是**平铺列表，点与点之间没有关系**，导致"从补给区到控制区怎么走"只能靠直线距离硬算 —— 而 2026 场地有高地挡路，直线距离会骗人。所以我们的点表**带显式邻接边**（§4.4）。

### 4.2 2026 场地几何（官方真值，逐项有出处）

坐标系：**场地角点为原点，单位米**，`x ∈ [0, 12]`（长），`y ∈ [0, 8]`（宽）。红方在 `y` 大的一侧。

| 要素 | 官方尺寸 | 坐标（米） | 出处 | 置信度 |
|---|---|---|---|---|
| 战场 | 12000 × 8000 mm | x∈[0,12], y∈[0,8] | 图 3-3 | ✅ 高 |
| **控制区** | **3000 × 3000 正方形** | **x∈[4.5, 7.5], y∈[2.5, 5.5]**（中心 = (6.0, 4.0)） | 图 3-7 / 3-8 + §3.2.4 文字"位于战场的中心位置" | ✅ 高 |
| 补给区（兼启动区） | 1500 × 2000 | 红：x∈[0, 1.5], y∈[6.0, 8.0]<br>蓝：x∈[10.5, 12.0], y∈[0, 2.0] | 图 3-4 + 图 3-3 位置 | ✅ 中高 |
| **高地**（2026 新增） | 长 **5000** × 宽 **2000**，总高 **400**（含 **200** 分阶），内侧 **150** 窄条 | 红：x∈[2.5, 4.5], y∈[3.0, 8.0]<br>蓝：x∈[7.5, 9.5], y∈[0, 5.0] | 图 3-3 尺寸链（2500/4350/4500；2500/3000/3900）+ 图 3-6 | ✅ 尺寸高 / ⚠️ 三维形状待定（§9.1） |

不加边的点表 = 一堆孤立坐标，无法回答"怎么绕开高地过去"。边用**直线可通行**判定（与高地/场地边界做线段相交检查，借鉴 2D 哨兵环境的 `segment` 函数，MIT）。

MID_R       -- SUPPLY_R, HOME_R, HL_R_MID
HL_R_MID    -- MID_R, HL_R_IN, HL_R_TOP
HL_R_IN     -- HL_R_MID, HL_R_TOP, ZONE_W, ZONE_NW, ZONE_SW
HL_R_TOP    -- HL_R_MID, HL_R_IN                      # 仅当可攀爬

ZONE_NW/SW  -- HL_R_IN, ZONE_W, ZONE_C, ZONE_N/S
ZONE_N/S    -- ZONE_W, ZONE_C, ZONE_NW/SW, ZONE_E
ZONE_E      -- ZONE_C, ZONE_N, ZONE_S, ENEMY_SUPPLY_WATCH

## 5. 行为决策树设计

### 5.1 结构：单层 ReactiveFallback + 4 棵子树

**为什么是 4 棵而不是中科大的 6 棵**（结论已与队伍负责人确认）：

中科大的 6 棵是被**6 个独立输出通道**逼出来的：`tactical_mode`（模式位）/ `nav_goal`（位姿）/ `desired_stance`+`desired_lifter_pos`（**升降机构**）/ 资源服务请求 / `cmd_vel`（脱困）/ 云台。

映射到我们（动作空间只有 `move[2]` / `target` / `fire` 三个通道）：

| 中科大 | 我们 | 判定 |
|---|---|---|
| `tactical` | 战术模式（占点/交战/撤退/补给） | ✅ 要 |
| `nav` | 子目标点（消费战术点图） | ✅ 要 |
| `resource` | 复活 / 兑换 / **解除虚弱** | ✅ 要（且我们多一条） |
| `gimbal` | **开火门控 + 目标选择** | ✅ 要，改名 `combat` |
| `stance` + `lifter` | 我们**无升降/姿态机构**，环境也没有 | ❌ 空壳 |
| `recovery` | 环境**无卡死建模** | ⚠️ **降级为兜底分支**（2027 上隧道后独立成第 5 棵） |

> **拆树的判据**（写成规则，防止以后随意加树）：**当且仅当出现一个「独立输出通道 + 独立生命周期 + 独立失败模式」时，才拆一棵新树。**
> 按此判据，**2027 必须加第 5 棵 `recovery`**：隧道口脱困是独立失败模式 + 独立输出（速度指令）。
> 中科大为此专门有 `TunnelRecoveryConfig{通过偏航角, vx, vy, 固定朝向}` 与独立的 `recovery_tree.xml`。

**代价（必须知道）**：中科大自己的 README「已知问题」原文承认 ——
> 多棵树共享 blackboard，同一 key 可能存在多个条件节点或 action 写入者；**缺少字段级版本/所有权约束，修改时必须人工审计读写链**。

他们实测也确实积压了大量注释分支（`tactical_tree.xml` 的 `DefendPriority` 整段注释；`resource_tree.xml` 6 条分支注释掉 3 条）。**我们靠"单写者契约"（§5.3）+ 单测来防这个问题，而不是靠加树。**

### 5.2 优先级栈（根节点 = 单层 ReactiveFallback，顺序即优先级）

```
默认 ReactiveFallback（顺序 = 优先级，任一条成功即停止）
├─ 1  Dead        : 死亡 / 复活读条中        → 静止 + 开火门控=0
├─ 2  Weak        : 虚弱中（复活后未接触己方补给区）
│                  → nav_goal = SUPPLY_R；开火门控=0
│                  ★ 依据：官方手册 §3.3.2.2（⚠️ 无开源依据，见 §5.5）
├─ 3  LowResource : 低血（进出双阈值）或 低弹 → nav_goal = SUPPLY_R（回血 / 兑换）
├─ 4  Overheat    : 热量 > 上限 × 87.5%      → 开火门控=0（移动照常）
├─ 5  ContestZone : 敌在控制区内             → nav_goal = 区内有利点；combat 选目标+开火
├─ 6  HoldZone    : 控制区可占              → nav_goal = ZONE_C；combat 按可见性开火
└─ 7  Fallback    : 无条件（**必须存在**）    → nav_goal = HOME_R + 自转搜索
```

**第 7 条是无条件兜底，不可省略** —— 这是三层兜底里的"第 2 层永远可用"在树内的体现，也是 Artinx（`patrol_key_facilities fallback="true"`）与 pb2025（`KeepRunningUntilFailure`）共同的做法。

### 5.4 阈值与迟滞

| 参数 | 初值 | 基准 | 出处 / 理由 |
|---|---|---|---|
| `hp_retreat_enter` | 上限 × **0.30** = 120 | 上限 400 | 借鉴 `guganav`（Apache-2.0）`hp_survival_enter=120` |
| `hp_retreat_exit` | 上限 × **0.75** = 300 | 上限 400 | 借鉴 `guganav` `hp_survival_exit=300`；**双阈值迟滞防抖** |
| `heat_stop_ratio` | **0.875** | 热量上限 260（2026） | 借鉴 pb2025（Apache-2.0）：`heat_max=350/400`；**留余量不贴上限** |
| `ammo_low` | 60（**待标定**） | 初始 750 | ⚠️ 无开源依据，标定见 §8 |
| `target_switch_confirm` | **3 帧**（10 Hz = 0.3 s） | — | 借鉴哈工大"投票迟滞"思想（MIT）；哈工大 40 帧 ≈ 1.2 s，我们按同物理量级下调并**待调** |
| `motion_mode_confirm` | 5 帧 | — | 同上 |
| 决策周期 | **10 Hz** | — | 三个独立来源印证：中科大 `bt_loop_duration=100ms`、wdr26 `tick_period=100`、guganav `tick 20Hz`(另说) |

**⚠️ 阈值有效性有前置条件（本文档最重要的一条工程约束）**

`hp_retreat_enter=120` 只有**在"补给区回血已建模"的前提下**才成立（§3）。官方 §3.3.2.1：占领己方补给区回血 **25% 上限/秒** = 哨兵 **100 HP/s**。
而当前环境 `heal_supply_per_s = 0.0`（**关掉了**）→ 若直接上线，哨兵会**复活即进入撤退且永远回不满血**，重演 §3 的翻车。

**处置（落实 `开源借鉴.md §0.1` 的"把这类关系写成代码自检"）**：
```python
# 借鉴：开源借鉴.md §0.1「照抄阈值前必须核对场景可比性」
# 关系：撤退阈值必须能在补给区被"解除"，否则策略永久处于撤退状态（已翻车一次）
if heal_supply_per_s <= 0.0 and hp_retreat_enter >= max_hp * respawn_hp_ratio:
    raise ValueError(
        "回血未建模时，撤退阈值必须低于复活血量，否则复活即永久撤退。"
        "见 开源借鉴.md §0.1 / 本文档 §3。")
```

### 5.5 「虚弱」——**显式标注：无开源依据**

**依据只能是官方手册**（`RoboMaster_2026_...V1_2_0...txt:1097-1103` 原文）：

> 机器人复活后，血量恢复至上限血量的20%，暂时处于无敌状态，持续时间为 **30 秒**，同时进入"**虚弱**"状态。"虚弱"状态下的机器人具有以下特点：**发射机构锁定**、**无法占领控制区**。此后，在其**检测到己方补给区场地交互模块卡**时，"虚弱"和无敌状态解除。

**开源覆盖情况（实测）**：

| 实现 | 覆盖程度 |
|---|---|
| 西电 `sentry_desicion` | 有 `need_unlock`（复活锁发射 / 回补给区解除）✅ 但 **无"不能占控制区"判断**，且 **`rmul2024.xml` 未引用该节点** |
| Artinx 仿真 | 有完整链条（`weaken_duration=30.0`、`clear_weak=True`）⚠️ 但那是**仿真自设规则**，非官方条款 |
| 中科大 / pb2025 / 哈工大 / guganav / wdr26 | **完全没有** |
| 当前环境 `rmul_3v3_env.py` | **完全没有**（且 `respawn_invuln=10.0`，官方是 **30 s**） |

⇒ 决策树的第 2 条分支与环境的虚弱建模**必须自研**，按 `开源借鉴.md §5` 在代码里显式标注：
```python
# ⚠️ 无开源依据（未找到覆盖 RMUL 2026 虚弱语义的对口实现）：本项为自研，风险自负
# 依据：RMUL 2026 手册 V1.2.0 §3.3.2.2 原文（复活后锁发射 + 不能占控制区，需回己方补给区解除）
```

2. `raw.githubusercontent.com` **时通时断**：前期可用返回纯文本，后期整体 `fetch failed` —— 是唯一不占限流的通路，应作为主力并**带重试**
3. `data.jsdelivr.com/v1/packages/gh/<owner>/<repo>@<branch>?structure=flat` 可一次列整仓目录，但 **>50 MB 仓库返回 403**
4. `web_fetch` 输出**上限约 100 KB** → **任何 >1 MB 的二进制（PDF/PNG/PGM/zip）在沙箱内取不到**，别浪费轮次
5. **沙箱内 `pwsh` 出站网络被封**（`Invoke-WebRequest` 对 `raw` 与 `ghproxy.net` 均报"基础连接已经关闭"）→ **只有 `web_fetch` 能出网**
